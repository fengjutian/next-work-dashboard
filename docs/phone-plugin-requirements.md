# Phone 局域网通信插件需求文档

> 文档状态：Draft 1.0  
> 产品名称：Phone  
> 插件 ID：`phone`  
> 首期平台：Windows 桌面端（Electron）  
> 产品范围：局域网内桌面端一对一文字、文件、语音和视频通信

## 1. 产品概述

Phone 是 `next-work-dashboard / prompt-lab` 的内置局域网通信插件。处于同一局域网的两台电脑安装并启用 Phone 后，可以自动发现彼此，经用户确认配对后进行一对一文字聊天、文件传输、语音通话和视频通话。

Phone 默认不依赖互联网、云服务或中心账号系统。设备身份、联系人、消息记录和接收文件均保存在本机；实时音视频优先通过 WebRTC 在两台设备之间点对点传输。

### 1.1 产品目标

- 在办公室、家庭、实验室等可信局域网中提供简单、快速的设备间通信。
- 支持桌面端之间发送文字和任意类型文件。
- 支持一对一语音与视频通话。
- 保证设备身份明确、通信须经授权、传输结果可确认。
- 建立通用 Peer 协议，为后续接入 Android、iOS 和其他桌面平台留出空间。

### 1.2 非目标

首期不提供：

- 群聊、群语音或多人视频会议。
- 公网穿透、互联网账号、云端消息同步。
- 手机端客户端。
- 朋友圈、公众号、小程序、支付等社交平台功能。
- 服务端永久代收离线消息。
- 端到端加密身份体系的跨设备云备份。
- 语音消息、屏幕共享和远程控制。

## 2. 核心原则

1. **桌面端优先**：第一版只保证 Phone 桌面端之间互通。
2. **一对一通信**：每个会话只有两个参与设备，每次通话仅允许两方加入。
3. **本地优先**：发现、配对、聊天、文件和音视频均在局域网内完成。
4. **显式信任**：发现设备不等于可信设备，首次通信必须由接收方确认。
5. **可靠消息**：文字和文件消息具有唯一 ID、状态确认、去重和失败重试能力。
6. **媒体不落盘**：实时语音和视频默认不录制、不保存。
7. **协议通用化**：使用 `peerDeviceId` 等中性命名，不使用 `phoneDeviceId`、`sendToPhone` 等终端限定模型。

## 3. 用户角色与场景

### 3.1 用户角色

- **本机用户**：当前 Phone 插件的操作者。
- **局域网联系人**：已发现但尚未配对，或已配对且受信任的另一台设备。

### 3.2 典型场景

- 用户在两台同网电脑间发送一段文字或代码片段。
- 用户将文档、图片、压缩包从电脑 A 发送到电脑 B。
- 用户看到同事在线后发起语音通话。
- 用户在文字聊天中升级为视频通话。
- 对方暂时离线时，消息保留在发送端，重新上线后自动尝试投递。

## 4. 信息架构与主界面

Phone 作为内置插件注册到 ActivityBar：

- `id`: `phone`
- `name`: `Phone`
- 默认状态：`enabled: false`
- 建议 `keepAlive: true`，避免切换插件时断开实时连接或通话。

主界面采用双栏布局：

### 4.1 左栏

- 本机设备名称、网络状态和设置入口。
- 搜索框。
- 会话列表：头像、设备名、最后一条消息、时间、未读数、在线状态。
- “发现设备”入口，显示局域网内可配对设备。

### 4.2 右栏

- 顶部：联系人名称、在线状态、语音通话、视频通话按钮。
- 中部：按时间排序的消息列表。
- 底部：文字输入框、发送文件按钮、发送按钮。
- 通话期间：悬浮或内嵌通话面板，显示远端画面、本地预览和控制栏。

### 4.3 全局通知

- 新消息通知。
- 来电通知，可接听或拒绝。
- 文件接收请求及结果通知。
- 设备上线、连接中断等重要状态提示。

用户正在查看对应会话时，不累计该会话未读数。

## 5. 功能需求

## 5.1 本机身份

首次启用 Phone 时生成并持久化：

- `deviceId`：不可变 UUID。
- `deviceName`：默认取系统计算机名，允许用户修改。
- 本机身份密钥或证书指纹。
- 协议版本和应用版本。

卸载插件时默认保留身份与历史；用户可在设置中执行“清除 Phone 数据”。

## 5.2 局域网发现

- 使用 mDNS 广播并发现 Phone 节点。
- 广播至少包含设备 ID、设备名、服务端口、协议版本和能力列表。
- 设备列表区分：未配对、已配对在线、已配对离线、不兼容。
- 同一 `deviceId` 的多条发现结果必须合并。
- 网络切换、休眠恢复后自动重新广播和发现。
- 不兼容协议版本不得建立会话，并显示明确原因。

## 5.3 配对与信任

- 用户选择设备并发起配对。
- 接收方必须看到请求方设备名和身份指纹，并主动接受或拒绝。
- 可使用六位配对码或双方确认码验证身份。
- 配对成功后双方保存可信设备信息和会话凭证。
- 用户可查看可信设备、修改备注、解除配对。
- 解除配对后旧凭证立即失效，后续连接必须重新配对。
- 未配对设备不能发送消息、上传文件或发起通话。

## 5.4 文字聊天

- 支持发送 UTF-8 纯文本和多行内容。
- 空白消息不得发送。
- 第一版单条消息最大 20,000 字符，超过时提示转为文件发送。
- Enter 发送，Shift+Enter 换行；允许在设置中切换发送快捷键。
- 消息展示发送时间和状态：发送中、已发送、已送达、已读、失败。
- 支持复制消息、删除本地记录和重试失败消息。
- 接收方按 `messageId` 去重，重复投递不得生成两条消息。
- 双方在线时实时投递；对方离线时进入本机待发送队列，对方上线后自动重试。
- 已送达不等于已读；打开并查看会话后发送已读回执。
- 第一版不要求撤回、编辑、引用、表情包和富文本。

### 5.4.1 消息状态

```text
queued -> sending -> sent -> delivered -> read
                    \-> failed -> retrying
```

状态只能向前推进；重复或乱序回执不得令状态倒退。

## 5.5 文件传输

- 支持发送任意类型的单个或多个文件。
- 支持通过文件选择器和拖放发起发送。
- 文件消息显示名称、大小、类型、进度、速度和状态。
- 接收方可接受、拒绝、取消；设置中可配置可信设备自动接收策略。
- 默认保存到用户配置的 Phone 下载目录。
- 文件传输使用 HTTP 流或独立数据通道，不将二进制内容编码进聊天 WebSocket。
- 每个文件生成稳定 `fileId`，传输完成后校验 SHA-256。
- 文件名必须清理，禁止绝对路径和 `..` 路径穿越。
- 同名文件不得静默覆盖，应自动重命名或询问用户。
- 支持传输进度、取消、失败重试；MVP 可不支持断点续传，但协议中应保留 `offset` 和分片能力。
- 默认单文件上限 10 GB，可在设置中降低；磁盘空间不足时应在写入前或传输中安全失败。
- 文件发送成功后，双方聊天记录中均保留文件元数据；删除聊天消息不默认删除本地文件。

### 5.5.1 文件状态

```text
offered -> accepted -> transferring -> verifying -> completed
       \-> rejected      \-> failed / cancelled
```

## 5.6 语音通话

- 用户可以从已配对且在线的会话中发起一对一语音通话。
- 接收方显示来电设备、接听和拒绝操作。
- 呼叫方可在接通前取消；无人接听默认 30 秒超时。
- 通话中支持麦克风静音、扬声器静音、挂断。
- 支持选择麦克风和输出设备；设备被拔出时自动回退并提示。
- 显示通话状态、通话时长和连接质量。
- 同一设备同一时间只允许一个活动通话；已有通话时对新来电回复忙线。
- 通话结束必须停止媒体轨道并释放 `RTCPeerConnection`。

## 5.7 视频通话

- 视频通话包含双向音频和双向视频。
- 支持本地预览和远端主画面。
- 支持开关摄像头、静音麦克风、选择摄像头和挂断。
- 关闭摄像头时保持音频通话，不结束整个会话。
- 摄像头不可用时可降级为语音通话，并清晰提示。
- 第一版不要求美颜、背景虚化、录制、屏幕共享和通话中邀请第三人。
- 默认约束建议为 720p、30fps，并根据网络和设备能力自适应。

## 5.8 通话状态机

```text
idle
  -> inviting -> ringing -> connecting -> connected -> ending -> ended
             \-> rejected
             \-> cancelled
             \-> timeout
             \-> busy
connecting/connected -> failed
```

- 每次通话使用唯一 `callId`。
- 所有信令必须同时携带 `callId`、发送方、接收方和时间戳。
- 重复信令必须幂等处理。
- 双方同时呼叫时，应按稳定规则解决冲突，避免 Offer glare。
- ICE 需支持 Trickle ICE；远端描述尚未设置时缓存 candidate。
- `disconnected` 短暂状态允许尝试 ICE restart，超过阈值后结束通话。

## 5.9 历史记录与搜索

- 本地保存会话、文字消息、文件消息、回执和通话记录。
- 会话按最后活动时间倒序排列。
- 支持按联系人和消息文字搜索。
- 通话记录包括类型、方向、开始时间、结束时间和结果，不保存媒体内容。
- 支持清空单个会话记录。
- 支持配置消息保留期限；默认永久保留，直到用户删除。

## 5.10 设置

- 设备名称。
- 下载目录。
- 启动时启用 Phone。
- 新消息、来电和文件通知开关。
- 麦克风、摄像头、扬声器默认设备。
- 文件自动接收策略和大小限制。
- 消息保留策略。
- 可信设备管理。
- 网络诊断信息：本机 IP、监听端口、mDNS、协议版本。

## 6. 协议需求

控制消息通过已认证 WebSocket 传输，建议统一信封：

```ts
interface PhoneEnvelope<T = unknown> {
  version: 1;
  id: string;
  type: string;
  fromDeviceId: string;
  toDeviceId: string;
  sentAt: number;
  payload: T;
}
```

首期消息类型至少包括：

```text
peer.hello
peer.ping / peer.pong
chat.text
chat.file.offer / accept / reject / progress / complete / cancel
chat.delivered / chat.read
call.invite / ringing / accept / reject / cancel / busy / hangup
webrtc.offer / answer / ice / restart
error
```

### 6.1 可靠性要求

- 每个业务消息具有全局唯一 ID。
- 接收端必须持久化成功后再回复 `delivered`。
- 发送端在超时后按退避策略重试。
- 接收端按消息 ID 幂等处理。
- 重连后双方交换最后同步游标或待确认消息 ID。
- 系统时钟仅用于展示，不用于唯一性和严格顺序判断。

## 7. 数据模型

建议至少包含以下实体：

### 7.1 Peer

```ts
interface PhonePeer {
  id: string;
  name: string;
  remark?: string;
  fingerprint: string;
  trustedAt: number;
  lastSeenAt?: number;
  status: 'online' | 'offline' | 'incompatible';
  capabilities: string[];
}
```

### 7.2 Conversation

```ts
interface PhoneConversation {
  id: string;
  peerId: string;
  lastMessageAt?: number;
  unreadCount: number;
}
```

### 7.3 Message

```ts
interface PhoneMessage {
  id: string;
  conversationId: string;
  senderId: string;
  recipientId: string;
  kind: 'text' | 'file' | 'call';
  text?: string;
  fileId?: string;
  createdAt: number;
  status: 'queued' | 'sending' | 'sent' | 'delivered' | 'read' | 'failed';
}
```

### 7.4 FileTransfer 与 Call

文件记录需包含文件名、MIME、大小、SHA-256、本地路径、方向、进度和状态。通话记录需包含 `callId`、Peer、语音/视频类型、方向、状态、开始/接通/结束时间和结束原因。

## 8. 技术架构约束

```text
Phone Desktop A                         Phone Desktop B
Electron Renderer                       Electron Renderer
  Chat UI + WebRTC                        Chat UI + WebRTC
          | IPC                                   | IPC
Electron Main                            Electron Main
          | JSONL/RPC                              | JSONL/RPC
Rust Phone sidecar  <--- WS/HTTP/WebRTC ---> Rust Phone sidecar
  mDNS + auth + routing + storage          mDNS + auth + routing + storage
```

- Phone 必须作为独立插件实现，目录建议为 `src/plugins/phone/`。
- 网络、存储和敏感权限放在 Main/sidecar，不在 Renderer 中直接暴露文件系统能力。
- 可复用 MyCast 的 mDNS、配对、HTTP 文件流、WebSocket 和 WebRTC 信令代码，但应抽取公共模块或复制后通用化，不能破坏现有 MyCast 功能。
- 新增 IPC channel 时必须同步 Main handler、preload bridge 和 `src/types/electron.d.ts`。
- 如新增 `nwd-phone.exe` sidecar，必须更新 `forge.config.ts` 的 `extraResource` / `asar.unpack`。
- Renderer 使用 Chromium 原生 `RTCPeerConnection`、`getUserMedia` 和媒体设备 API。

## 9. 安全与隐私

- 未配对 Peer 的业务请求一律拒绝。
- 配对后连接使用设备凭证认证，不长期复用六位配对码。
- 建议使用 TLS 或基于设备密钥建立加密通道；WebRTC 媒体必须使用其标准 DTLS-SRTP。
- 身份指纹变化时中止自动连接并要求重新确认。
- 限制消息、帧、文件名和上传体积，防止内存或磁盘耗尽。
- 所有接收路径必须限定在配置目录内。
- 日志不得记录消息正文、凭证、SDP 中的敏感网络信息或文件内容。
- 摄像头和麦克风只在用户发起或接受通话后启用；通话结束立即释放。
- 提供清除聊天记录、文件索引、可信设备和身份数据的操作。

## 10. 异常与边界处理

- 对方离线：文字/文件邀请进入待发送队列；通话按钮禁用或提示离线。
- 网络切换：重新发现和连接；聊天自动同步，通话可尝试一次 ICE restart。
- 应用休眠/退出：关闭连接、停止媒体、将未确认消息保留为待发送。
- 对方版本不兼容：不连接并展示双方协议版本。
- 文件源在发送前被删除或修改：中止并提示重新选择。
- 接收磁盘不足或无权限：拒绝或中止传输，不留下伪完成记录。
- 摄像头/麦克风权限拒绝：提示设置路径，允许视频降级为语音。
- 双方同时建立连接：按 `deviceId` 排序确定唯一主动连接方，合并重复连接。
- 双方同时发起通话：按 `callId`/设备 ID 的稳定规则保留一条呼叫。

## 11. 非功能需求

- 空闲状态 CPU 使用应接近零，不持续轮询媒体设备。
- 常驻内存和 sidecar 资源应可控；插件禁用后释放监听端口和连接。
- 同网可达设备在正常环境下 5 秒内出现。
- 在线文字消息在正常局域网下 1 秒内显示。
- 通话从接听到出现媒体目标不超过 5 秒。
- 1 GB 文件传输过程中不得将整个文件读入内存。
- 应支持至少 100,000 条本地消息记录而不显著阻塞主界面。
- UI、协议和存储错误必须可诊断，但不得泄露秘密。

## 12. MVP 验收标准

满足以下条件可认为桌面端 MVP 完成：

1. 两台 Windows 电脑在同一局域网启用 Phone 后能互相发现。
2. 未配对设备不能通信；双方确认后能保存信任关系并自动重连。
3. 双方可以互发中英文、多行文字；重复投递不产生重复消息。
4. 消息能正确展示发送中、已送达、已读和失败状态。
5. 对方离线期间发送的文字，在对方重新上线后能自动送达。
6. 双方可以互传至少 1 GB 文件，显示进度，并通过 SHA-256 校验。
7. 文件拒绝、取消、网络中断和磁盘不足均有明确结果，不误报完成。
8. 双方可以发起、接听、拒绝和挂断一对一语音通话。
9. 双方可以进行双向音视频通话，并独立开关麦克风和摄像头。
10. 忙线、无人接听、权限拒绝和连接失败均能正确结束状态机。
11. 挂断后摄像头指示灯熄灭，麦克风和 WebRTC 资源被释放。
12. 重启应用后，可信设备、会话、消息、文件元数据和通话记录仍可查看。
13. 禁用 Phone 插件后不再广播服务，不保留活动网络监听或媒体轨道。

## 13. 测试要求

### 13.1 单元测试

- 消息状态推进与乱序回执。
- 消息去重和离线重试。
- 文件名清理、路径约束、大小限制和哈希校验。
- 呼叫状态机的正常及异常分支。
- 重复连接和同时呼叫的冲突解决。

### 13.2 集成测试

- 两个本地 sidecar 的发现、配对、认证和重连。
- 双向文本及回执。
- 双向文件流、取消和校验失败。
- WebRTC Offer/Answer/ICE 信令往返。
- IPC handler、preload 和类型契约一致性。

### 13.3 手工验收矩阵

- Windows 10 ↔ Windows 10。
- Windows 10 ↔ Windows 11。
- Windows 11 ↔ Windows 11。
- 有线 ↔ Wi-Fi、Wi-Fi ↔ Wi-Fi。
- 防火墙阻止、网络切换、休眠恢复。
- 无摄像头、无麦克风、权限拒绝、设备通话中被拔出。

## 14. 分期计划

### Phase 1：通信底座

- Phone 插件骨架和 sidecar。
- 通用 Peer 模型、mDNS 发现、配对、信任和连接管理。
- 本地数据库和协议版本协商。

### Phase 2：文字聊天

- 会话 UI、文字消息、回执、未读、历史和离线重试。

### Phase 3：文件传输

- 文件邀请、流式收发、进度、取消、重试、哈希与下载目录。

### Phase 4：语音通话

- 呼叫状态机、WebRTC 音频、来电 UI、静音和设备选择。

### Phase 5：视频通话

- 双向视频、本地预览、摄像头控制、网络统计与异常恢复。

### Phase 6：稳定性与发布

- 防火墙引导、诊断、性能优化、完整 E2E、安全审查和打包验证。

## 15. 后续候选能力

- Android/iOS 客户端接入同一 Peer 协议。
- 语音消息、截图粘贴、消息引用和表情。
- 屏幕共享。
- 断点续传和目录传输。
- 群聊；多人音视频需单独评估 SFU，不在一对一 P2P 上直接堆叠。
- 可选端到端加密身份恢复和跨设备历史迁移。
